1. [Jointures] Écrire la condition de jointure

QCU, une seule réponse · bonne réponse en D

Objectif : Relier la clé étrangère d'une table à la clé primaire de l'autre.

Schéma : ELEVE (id_e, nom, #id_classe) et CLASSE (id_classe, nom_c).

Quelle est la condition de jointure correcte entre ELEVE et CLASSE ?

  1. ON ELEVE.id_e = CLASSE.id_classeid_e identifie l'élève, pas sa classe : l'élève n° 2 serait relié à la classe n° 2 par hasard. On relie la clé étrangère à la clé primaire.
  2. WHERE ELEVE.nom = CLASSE.nom_cUn nom d'élève n'est jamais égal à un nom de classe : on n'obtiendrait rien. La jointure se fait sur les identifiants.
  3. JOIN ON ELEVE = CLASSEOn ne compare pas deux tables entières : il faut dire quels attributs doivent être égaux, ici les id_classe.
  4. Juste · ON ELEVE.id_classe = CLASSE.id_classeOui : la clé étrangère #id_classe de ELEVE est égale à la clé primaire id_classe de CLASSE. Chaque élève est relié à sa classe.

2. [Jointures] Afficher des colonnes de deux tables

QCU, une seule réponse · bonne réponse en D

Objectif : Écrire une jointure complète, sans produit cartésien.

Schéma : ELEVE (id_e, nom, #id_classe) et CLASSE (id_classe, nom_c).

Quelle requête affiche le nom de chaque élève et le nom de sa classe ?

  1. SELECT nom, nom_c FROM ELEVE, CLASSE;Sans condition, on obtient un produit cartésien : chaque élève associé à toutes les classes. 3 élèves et 2 classes donnent 6 lignes.
  2. SELECT nom, nom_c FROM ELEVE JOIN CLASSE;SQLite accepte un JOIN sans ON, mais il fait alors un produit cartésien, comme une virgule : chaque élève avec chaque classe. La condition ON est indispensable.
  3. SELECT nom, nom_c WHERE ELEVE JOIN CLASSE;L'ordre des clauses est fixe : SELECT, FROM (avec les tables et le JOIN), puis WHERE. Ici, SQLite signale une erreur de syntaxe.
  4. Juste · SELECT nom, nom_c FROM ELEVE JOIN CLASSE ON ELEVE.id_classe = CLASSE.id_classe;Oui : JOIN … ON garde seulement les paires où la classe de l'élève est bien cette classe. On obtient une ligne par élève.

3. [Jointures] Une jointure suivie d'un filtre

QCU, une seule réponse · bonne réponse en C

Objectif : Filtrer sur un attribut d'une autre table grâce à une jointure.

Schéma : VILLAGE (id_v, nom_v) et PIROGUE (id_p, nom_p, couleur, #id_v).

Quelle requête affiche les noms des pirogues du village de Bouéni ?

  1. SELECT nom_p FROM PIROGUE WHERE nom_v = 'Bouéni';nom_v n'est pas un attribut de PIROGUE : SQLite répond « no such column: nom_v ». Il faut d'abord joindre VILLAGE.
  2. SELECT nom_p FROM PIROGUE JOIN VILLAGE WHERE nom_v = 'Bouéni';Sans ON, SQLite associe chaque pirogue à chaque village : toutes les pirogues ressortent avec le village de Bouéni, même celles de Sada.
  3. Juste · SELECT nom_p FROM PIROGUE JOIN VILLAGE ON PIROGUE.id_v = VILLAGE.id_v WHERE nom_v = 'Bouéni';Oui : la jointure relie chaque pirogue à son village, puis WHERE garde celles de Bouéni.
  4. SELECT nom_p FROM PIROGUE, VILLAGE WHERE nom_v = 'Bouéni';C'est un produit cartésien : la condition de jointure manque. Toutes les pirogues seraient affichées, pas seulement celles de Bouéni.

4. [Jointures] Joindre trois tables

QCU, une seule réponse · bonne réponse en B

Objectif : Enchaîner deux jointures en suivant les clés étrangères.

Schéma : ZONE (id_z, nom_z) ; RECIF (id_r, nom_r, #id_z) ; MESURE (id_m, valeur, #id_r).

Quelle clause FROM relie correctement les zones aux mesures ?

  1. FROM ZONE JOIN MESURE ON ZONE.id_z = MESURE.id_rMESURE n'a pas de lien direct avec ZONE : comparer un identifiant de zone à un identifiant de récif relie des lignes au hasard. Il faut passer par RECIF.
  2. Juste · FROM ZONE JOIN RECIF ON ZONE.id_z = RECIF.id_z JOIN MESURE ON RECIF.id_r = MESURE.id_rOui : on suit les clés étrangères, de MESURE vers RECIF, puis de RECIF vers ZONE. Une condition ON pour chaque JOIN.
  3. FROM ZONE, RECIF, MESURESans condition, c'est un produit cartésien de trois tables : chaque zone avec chaque récif et chaque mesure. Le résultat est faux et très long.
  4. FROM ZONE JOIN RECIF JOIN MESURE ON id_z = id_rid_z existe dans ZONE et dans RECIF : SQLite répond « ambiguous column name ». Chaque jointure a besoin de sa propre condition, avec le nom de la table devant.

5. [SQL] La profondeur maximale : MAX

QCU, une seule réponse · bonne réponse en B

Objectif : Obtenir la plus grande valeur d'une colonne avec MAX.

Schéma : PLONGEUR (id_plongeur, nom, #id_club) ; PLONGEE (id_plongee, lieu, profondeur, #id_plongeur), profondeur en mètres.

Quelle requête affiche la plus grande profondeur atteinte lors d'une plongée ?

  1. SELECT MAX(*) FROM PLONGEE;MAX s'applique à une colonne précise, celle dont on veut la plus grande valeur : SQLite refuse MAX(*).
  2. Juste · SELECT MAX(profondeur) FROM PLONGEE;Oui : MAX renvoie la plus grande valeur de la colonne (25 m ici). Pas besoin de jointure : on ne demande que la valeur. MIN donnerait la plus petite.
  3. SELECT profondeur FROM PLONGEE ORDER BY profondeur;Ce tri est croissant : la première ligne est la profondeur la plus faible, et toutes les plongées sont affichées. Il faudrait DESC, ou plus simplement MAX.
  4. SELECT AVG(profondeur) FROM PLONGEE;AVG calcule la moyenne des profondeurs, pas la plus grande.

6. [Jointures] Deux colonnes de même nom

QCU, une seule réponse · bonne réponse en A

Objectif : Préfixer un attribut par le nom de sa table pour lever une ambiguïté.

Les tables PLONGEUR (id_plongeur, nom, #id_club) et CLUB (id_club, nom) ont toutes deux un attribut nom.

Dans une jointure de ces deux tables, comment désigner le nom du plongeur ou de la plongeuse ?

  1. Juste · PLONGEUR.nomOui : table.attribut lève l'ambiguïté. Sans préfixe, SQLite répondrait « ambiguous column name: nom ».
  2. nom.PLONGEURL'ordre est inversé : on écrit d'abord la table, puis l'attribut. SQLite chercherait une table nommée nom.
  3. PLONGEUR->nomLa flèche n'est pas la notation d'un attribut de table en SQL. On écrit la table, un point, puis l'attribut.
  4. PLONGEUR(nom)Les parenthèses servent aux fonctions. Ici, SQLite lit d'abord nom, qu'il trouve dans les deux tables, et répond « ambiguous column name ». On écrit PLONGEUR.nom.

7. [Jointures] Oublier la condition : le produit cartésien

QCU, une seule réponse · bonne réponse en C

Objectif : Prévoir le résultat d'une requête sur deux tables sans condition de liaison.

La table PIROGUE a 4 lignes, la table VILLAGE en a 3. On exécute SELECT * FROM PIROGUE, VILLAGE;, sans condition.

Que se passe-t-il ?

  1. Le SGBD choisit tout seul la bonne liaisonLe SGBD ne devine jamais la liaison : sans condition, il associe tout avec tout. C'est à la requête de dire quelles colonnes doivent être égales.
  2. La requête provoque une erreur de syntaxeLa requête est valide : elle s'exécute. Mais elle donne toutes les combinaisons, ce qui n'est en général pas le résultat voulu.
  3. Juste · On obtient les 12 combinaisons possibles : c'est un produit cartésienOui : chaque pirogue est associée à chaque village, 4 × 3 = 12 lignes. Il faut une condition de jointure pour ne garder que les bonnes paires.
  4. La requête ne renvoie aucune ligneC'est l'inverse : sans condition, aucune ligne n'est écartée. On obtient 4 × 3 = 12 lignes.

8. [Jointures] L'ordre des tables dans une jointure

QCU, une seule réponse · bonne réponse en D

Objectif : Savoir qu'une jointure ne dépend pas de l'ordre des tables.

Dans une jointure A JOIN B ON …, l'ordre des tables (A JOIN B ou B JOIN A) change-t-il les lignes obtenues ?

  1. Oui, les données obtenues sont différentesLa condition est la même dans les deux cas : les mêmes paires de lignes sont gardées. Seul l'ordre des colonnes avec SELECT * peut changer.
  2. Oui, SQL refuse l'un des deux sensLes deux sens sont acceptés : une jointure peut s'écrire à partir de n'importe laquelle des deux tables.
  3. Seulement si les tables ont plus de 100 lignesLa taille des tables ne change pas le résultat d'une jointure : les paires gardées sont les mêmes dans les deux sens.
  4. Juste · Non, les lignes obtenues sont les mêmesOui : la jointure garde les paires où la condition est vraie, dans un sens comme dans l'autre. Avec SELECT *, seules les colonnes changent de place.

9. [Jointures] Un alias de table avec AS

QCU, une seule réponse · bonne réponse en C

Objectif : Comprendre le rôle d'un alias de table.

À quoi sert AS dans FROM PIROGUE AS P JOIN VILLAGE AS V ON P.id_v = V.id_v ?

  1. À trier les tables avant la jointureLe tri s'écrit ORDER BY, à la fin de la requête. AS donne un autre nom, plus court, à une table.
  2. À créer une copie des tablesAucune table n'est copiée : P et V sont d'autres noms pour PIROGUE et VILLAGE, le temps de la requête.
  3. Juste · À donner un nom court aux tables, pour écrire la requête plus simplementOui : P et V sont des alias. On écrit P.id_v au lieu de PIROGUE.id_v ; ils n'existent que dans cette requête.
  4. À protéger l'accès aux donnéesLes droits d'accès se gèrent ailleurs, dans le SGBD. AS ne fait que renommer une table dans la requête.

10. [SQL] Renommer une colonne du résultat : AS

QCU, une seule réponse · bonne réponse en A

Objectif : Donner un alias à une colonne affichée.

Table : VILLAGE (id_v, nom_v).

Quelle requête affiche la colonne nom_v sous le titre village, sans modifier la table ?

  1. Juste · SELECT nom_v AS village FROM VILLAGE;Oui : AS donne un alias à la colonne, le temps de la requête. La table, elle, n'est pas modifiée.
  2. SELECT nom_v RENAME village FROM VILLAGE;RENAME sert à modifier la structure d'une table (ALTER TABLE … RENAME). Dans un SELECT, SQLite signale une erreur de syntaxe.
  3. SELECT nom_v IS village FROM VILLAGE;IS compare deux valeurs : SQLite cherche une colonne village pour la comparer à nom_v, et répond « no such column: village ».
  4. SELECT nom_v -> village FROM VILLAGE;La flèche ne renomme pas une colonne (dans SQLite, elle sert à lire du JSON) : SQLite cherche une colonne village et ne la trouve pas.

11. [SQL] Compter avec deux conditions

QCU, une seule réponse · bonne réponse en B

Objectif : Filtrer avec AND avant de compter.

Table : TORTUE (id_t, espece, poids), poids en kg.

Quelle requête donne le nombre de tortues vertes de plus de 100 kg ?

  1. SELECT COUNT(*) FROM TORTUE WHERE espece = 'verte' OR poids > 100;OR compte aussi les tortues vertes légères et les grosses tortues d'autres espèces : le nombre est trop grand.
  2. Juste · SELECT COUNT(*) FROM TORTUE WHERE espece = 'verte' AND poids > 100;Oui : WHERE garde les tortues vertes de plus de 100 kg, puis COUNT(*) compte ces lignes.
  3. SELECT SUM(*) FROM TORTUE WHERE espece = 'verte' AND poids > 100;SUM additionne des valeurs, il ne compte pas des lignes, et SQLite refuse SUM(*).
  4. SELECT * FROM TORTUE WHERE espece = 'verte' AND poids > 100;Le filtre est bon, mais cette requête affiche les tortues une à une ; elle ne donne pas leur nombre. Il faut COUNT(*).

12. [SQL] Deux conditions sur les plongées

QCU, une seule réponse · bonne réponse en D

Objectif : Combiner une condition sur un texte et une condition sur un nombre.

Table : PLONGEE (id_plongee, lieu, profondeur, #id_plongeur).

Quelle condition garde les plongées faites à Bandrélé à moins de 20 m de profondeur ?

  1. WHERE lieu = 'Bandrélé' OR profondeur < 20OR garderait aussi les plongées profondes de Bandrélé et les plongées peu profondes ailleurs. Les deux conditions doivent être vraies : AND.
  2. WHERE lieu = 'Bandrélé', profondeur < 20Les conditions ne se séparent pas par une virgule : SQLite signale une erreur de syntaxe.
  3. WHERE lieu = Bandrélé AND profondeur < 20Sans apostrophes, Bandrélé est lu comme un nom de colonne : SQLite répond « no such column ». Un texte s'écrit entre apostrophes.
  4. Juste · WHERE lieu = 'Bandrélé' AND profondeur < 20Oui : AND garde les plongées qui remplissent les deux conditions à la fois.

13. [SQL] Trouver l'erreur dans une requête

QCU, une seule réponse · bonne réponse en B

Objectif : Repérer qu'une valeur texte s'écrit entre apostrophes.

SELECT nom FROM CLIENT WHERE ville = Mamoudzou;

Pourquoi cette requête provoque-t-elle une erreur ?

  1. Mamoudzou doit être écrit en majusculesLes majuscules ne changent rien ici : MAMOUDZOU serait aussi lu comme un nom de colonne. Ce qui manque, ce sont les apostrophes.
  2. Juste · Il manque des apostrophes autour de MamoudzouOui : sans apostrophes, SQLite cherche une colonne nommée Mamoudzou et répond « no such column: Mamoudzou ». On écrit ville = 'Mamoudzou'.
  3. On ne peut pas filtrer sur une villeOn peut filtrer sur n'importe quel attribut. Le problème est l'écriture de la valeur.
  4. Il manque un point-virgule après SELECT nomLe point-virgule ne se met qu'à la fin de la requête complète, et il y est déjà.

14. [SQL] Limiter le nombre de lignes : LIMIT

QCU, une seule réponse · bonne réponse en A

Objectif : Garder seulement les premières lignes d'un résultat.

Table : PLONGEE (id_plongee, lieu, profondeur, #id_plongeur).

Quelle requête n'affiche que les 3 premières lignes du résultat ?

  1. Juste · SELECT * FROM PLONGEE LIMIT 3;Oui : LIMIT, à la fin de la requête, garde les 3 premières lignes. Avec ORDER BY avant, on choisit lesquelles.
  2. SELECT TOP 3 * FROM PLONGEE;TOP existe dans certains SGBD, mais pas dans SQLite, qui signale une erreur. SQLite (comme MySQL) utilise LIMIT.
  3. SELECT * FROM PLONGEE STOP 3;STOP n'est pas un mot-clé SQL : SQLite signale une erreur de syntaxe.
  4. SELECT * FROM PLONGEE WHERE row < 3;row n'est pas une colonne de la table : SQLite répond « no such column: row ». Le nombre de lignes se limite avec LIMIT.

15. [Mises à jour] Supprimer une ligne encore référencée

QCU, une seule réponse · bonne réponse en C

Objectif : Expliquer le rôle de l'intégrité référentielle lors d'une suppression.

Schéma : VILLAGE (id_v, nom_v) et PIROGUE (id_p, nom_p, couleur, #id_v). Le contrôle des clés étrangères est activé (dans SQLite : PRAGMA foreign_keys = ON).

On tente de supprimer un village alors que des pirogues y sont encore reliées. Que se passe-t-il ?

  1. Le village est supprimé, et ses pirogues aussiCela n'arrive que si la clé étrangère est déclarée avec ON DELETE CASCADE. Sans cette option, la suppression est refusée.
  2. Le village est supprimé, et la clé étrangère des pirogues passe à 0Le SGBD ne choisit jamais une valeur de remplacement tout seul. Sans option particulière, il refuse la suppression.
  3. Juste · Le SGBD refuse la suppression, pour préserver l'intégrité référentielleOui : supprimer le village laisserait des pirogues qui pointent vers un village inexistant. SQLite répond « FOREIGN KEY constraint failed ».
  4. Rien de spécial : la contrainte est ignoréeLe contrôle est activé : la contrainte est vérifiée à chaque modification. C'est son rôle.

16. [Mises à jour] Ajouter une ligne : INSERT

QCU, une seule réponse · bonne réponse en A

Objectif : Écrire une requête INSERT INTO … VALUES.

Table : NAVIRE (nom, tonnage, port).

Quelle requête ajoute un navire nommé « Mamoudzou Express », de 400 tonnes ?

  1. Juste · INSERT INTO NAVIRE (nom, tonnage) VALUES ('Mamoudzou Express', 400);Oui : INSERT INTO table (colonnes) VALUES (valeurs) ajoute une ligne. Le port, non donné, reste vide (NULL).
  2. ADD INTO NAVIRE VALUES ('Mamoudzou Express', 400);Le mot-clé de l'ajout est INSERT INTO, pas ADD : SQLite signale une erreur de syntaxe.
  3. UPDATE NAVIRE SET nom = 'Mamoudzou Express';UPDATE modifie des lignes qui existent déjà : ici, il renommerait tous les navires ! Pour ajouter une ligne, on utilise INSERT.
  4. INSERT INTO NAVIRE ('Mamoudzou Express', 400);Il manque le mot-clé VALUES devant les valeurs : SQLite les lit comme des noms de colonnes et signale une erreur.

17. [Mises à jour] Modifier une ligne : UPDATE

QCU, une seule réponse · bonne réponse en B

Objectif : Écrire un UPDATE … SET … WHERE qui ne modifie qu'une ligne.

Table : ECOLE (id_e, nom, ville).

Quelle requête change la ville de l'école n° 42 en « Mtsapéré » ?

  1. UPDATE ECOLE WHERE id_e = 42 SET ville = 'Mtsapéré';L'ordre est fixe : SET vient avant WHERE. Ici, SQLite signale une erreur de syntaxe.
  2. Juste · UPDATE ECOLE SET ville = 'Mtsapéré' WHERE id_e = 42;Oui : UPDATE table SET colonne = valeur WHERE condition. Seule la ligne n° 42 est modifiée.
  3. MODIFY ECOLE SET ville = 'Mtsapéré' WHERE id_e = 42;MODIFY n'est pas un mot-clé SQL : une modification de lignes s'écrit avec UPDATE.
  4. UPDATE ECOLE SET ville = 'Mtsapéré';Attention : sans WHERE, toutes les écoles de la table seraient placées à Mtsapéré. Le WHERE choisit les lignes à modifier.

18. [Mises à jour] Un UPDATE qui calcule

QCU, une seule réponse · bonne réponse en A

Objectif : Utiliser la valeur actuelle d'une colonne dans un UPDATE.

Table : RESERVOIR (id_r, nom, volume), volume en m³.

Quelle requête augmente de 10 m³ le volume de tous les réservoirs ?

  1. Juste · UPDATE RESERVOIR SET volume = volume + 10;Oui : pour chaque ligne, la nouvelle valeur est calculée à partir de l'ancienne. Sans WHERE, toutes les lignes sont concernées, comme demandé.
  2. SET volume = volume + 10 FROM RESERVOIR;Une requête de modification commence par UPDATE : ici, SQLite signale une erreur de syntaxe.
  3. UPDATE RESERVOIR volume + 10;Il manque SET et le signe = : on doit dire quelle colonne reçoit quelle valeur.
  4. SELECT volume + 10 FROM RESERVOIR;SELECT affiche les volumes augmentés, mais n'enregistre rien : la table n'est pas modifiée.

19. [Mises à jour] Supprimer une ligne : DELETE

QCU, une seule réponse · bonne réponse en C

Objectif : Écrire un DELETE FROM … WHERE.

Table : NAVIRE (nom, tonnage, port).

Quelle requête supprime le navire nommé « Vieux Port » ?

  1. REMOVE FROM NAVIRE WHERE nom = 'Vieux Port';REMOVE n'est pas un mot-clé SQL : la suppression de lignes s'écrit DELETE FROM.
  2. DELETE nom = 'Vieux Port' FROM NAVIRE;La condition se place après FROM, dans un WHERE : DELETE FROM table WHERE condition. Ici, SQLite signale une erreur.
  3. Juste · DELETE FROM NAVIRE WHERE nom = 'Vieux Port';Oui : DELETE FROM, suivi d'un WHERE, supprime seulement les lignes qui vérifient la condition.
  4. DROP FROM NAVIRE WHERE nom = 'Vieux Port';DROP supprime une table entière (DROP TABLE), pas une ligne. Il ne s'écrit pas avec FROM et WHERE.

20. [Mises à jour] Supprimer une table : DROP TABLE

QCU, une seule réponse · bonne réponse en D

Objectif : Distinguer la suppression des lignes et la suppression de la table.

Quelle requête supprime définitivement la table NAVIRE, avec toutes ses données ?

  1. DELETE TABLE NAVIRE;SQLite signale une erreur de syntaxe : DELETE s'écrit DELETE FROM et supprime des lignes, jamais la table elle-même.
  2. REMOVE TABLE NAVIRE;REMOVE n'est pas un mot-clé SQL. La suppression d'une table s'écrit DROP TABLE.
  3. DELETE * FROM NAVIRE;L'étoile n'a pas sa place dans un DELETE : SQLite signale une erreur. DELETE FROM NAVIRE; viderait la table, mais la garderait.
  4. Juste · DROP TABLE NAVIRE;Oui : DROP TABLE détruit la table, sa structure et son contenu. Après, toute requête sur NAVIRE échoue : « no such table ».
