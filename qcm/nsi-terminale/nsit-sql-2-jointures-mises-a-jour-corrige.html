Corrigé enseignant·e. Cette page donne les bonnes réponses et tous les retours. Elle sert à relire le quiz ; elle ne se donne pas aux élèves. L'aperçu sans réponses : nsit-sql-2-jointures-mises-a-jour.html.

1. [Jointures] Écrire la condition de jointure

QCU, une seule réponse

Objectif : Relier la clé étrangère d'une table à la clé primaire de l'autre.

Schéma : ELEVE (id_e, nom, #id_classe) et CLASSE (id_classe, nom_c).

Quelle est la condition de jointure correcte entre ELEVE et CLASSE ?

Bonne réponse : D

  1. Distracteur : ON ELEVE.id_e = CLASSE.id_classeRetour : id_e identifie l'élève, pas sa classe : l'élève n° 2 serait relié à la classe n° 2 par hasard. On relie la clé étrangère à la clé primaire.
  2. Distracteur : WHERE ELEVE.nom = CLASSE.nom_cRetour : Un nom d'élève n'est jamais égal à un nom de classe : on n'obtiendrait rien. La jointure se fait sur les identifiants.
  3. Distracteur : JOIN ON ELEVE = CLASSERetour : On ne compare pas deux tables entières : il faut dire quels attributs doivent être égaux, ici les id_classe.
  4. Bonne réponse : ON ELEVE.id_classe = CLASSE.id_classeRetour : Oui : la clé étrangère #id_classe de ELEVE est égale à la clé primaire id_classe de CLASSE. Chaque élève est relié à sa classe.

2. [Jointures] Afficher des colonnes de deux tables

QCU, une seule réponse

Objectif : Écrire une jointure complète, sans produit cartésien.

Schéma : ELEVE (id_e, nom, #id_classe) et CLASSE (id_classe, nom_c).

Quelle requête affiche le nom de chaque élève et le nom de sa classe ?

Bonne réponse : D

  1. Distracteur : SELECT ELEVE.nom, CLASSE.nom_c FROM ELEVE, CLASSE;Retour : Sans condition, on obtient un produit cartésien : chaque élève associé à toutes les classes. 3 élèves et 2 classes donnent 6 lignes.
  2. Distracteur : SELECT nom, nom_c FROM ELEVE JOIN CLASSE;Retour : SQLite accepte un JOIN sans ON, mais il fait alors un produit cartésien, comme une virgule : chaque élève avec chaque classe. La condition ON est indispensable.
  3. Distracteur : SELECT nom, nom_c WHERE ELEVE JOIN CLASSE ON ELEVE.id_classe = CLASSE.id_classe;Retour : L'ordre des clauses est fixe : SELECT, FROM (avec les tables et le JOIN), puis WHERE. Ici, SQLite signale une erreur de syntaxe.
  4. Bonne réponse : SELECT nom, nom_c FROM ELEVE JOIN CLASSE ON ELEVE.id_classe = CLASSE.id_classe;Retour : Oui : JOIN … ON garde seulement les paires où la classe de l'élève est bien cette classe. On obtient une ligne par élève.

3. [Jointures] Une jointure suivie d'un filtre

QCU, une seule réponse

Objectif : Filtrer sur un attribut d'une autre table grâce à une jointure.

Schéma : VILLAGE (id_v, nom_v) et PIROGUE (id_p, nom_p, couleur, #id_v).

Quelle requête affiche les noms des pirogues du village de Bouéni ?

Bonne réponse : C

  1. Distracteur : SELECT nom_p FROM PIROGUE WHERE nom_v = 'Bouéni';Retour : nom_v n'est pas un attribut de PIROGUE : SQLite répond « no such column: nom_v ». Il faut d'abord joindre VILLAGE.
  2. Distracteur : SELECT nom_p FROM PIROGUE JOIN VILLAGE WHERE nom_v = 'Bouéni';Retour : Sans ON, SQLite associe chaque pirogue à chaque village : toutes les pirogues ressortent avec le village de Bouéni, même celles de Sada.
  3. Bonne réponse : SELECT nom_p FROM PIROGUE JOIN VILLAGE ON PIROGUE.id_v = VILLAGE.id_v WHERE nom_v = 'Bouéni';Retour : Oui : la jointure relie chaque pirogue à son village, puis WHERE garde celles de Bouéni.
  4. Distracteur : SELECT nom_p FROM PIROGUE, VILLAGE WHERE nom_v = 'Bouéni';Retour : C'est un produit cartésien : la condition de jointure manque. Toutes les pirogues seraient affichées, pas seulement celles de Bouéni.

4. [Jointures] Joindre trois tables

QCU, une seule réponse

Objectif : Enchaîner deux jointures en suivant les clés étrangères.

Schéma : ZONE (id_z, nom_z) ; RECIF (id_r, nom_r, #id_z) ; MESURE (id_m, valeur, #id_r).

Quelle clause FROM relie correctement les zones aux mesures ?

Bonne réponse : B

  1. Distracteur : FROM ZONE JOIN MESURE ON ZONE.id_z = MESURE.id_rRetour : MESURE n'a pas de lien direct avec ZONE : comparer un identifiant de zone à un identifiant de récif relie des lignes au hasard. Il faut passer par RECIF.
  2. Bonne réponse : FROM ZONE JOIN RECIF ON ZONE.id_z = RECIF.id_z JOIN MESURE ON RECIF.id_r = MESURE.id_rRetour : Oui : on suit les clés étrangères, de MESURE vers RECIF, puis de RECIF vers ZONE. Une condition ON pour chaque JOIN.
  3. Distracteur : FROM ZONE, RECIF, MESURERetour : Sans condition, c'est un produit cartésien de trois tables : chaque zone avec chaque récif et chaque mesure. Le résultat est faux et très long.
  4. Distracteur : FROM ZONE JOIN RECIF JOIN MESURE ON id_z = id_rRetour : id_z existe dans ZONE et dans RECIF : SQLite répond « ambiguous column name ». Chaque jointure a besoin de sa propre condition, avec le nom de la table devant.

5. [SQL] La profondeur maximale : MAX

QCU, une seule réponse

Objectif : Obtenir la plus grande valeur d'une colonne avec MAX.

Schéma : PLONGEUR (id_plongeur, nom, #id_club) ; PLONGEE (id_plongee, lieu, profondeur, #id_plongeur), profondeur en mètres.

Quelle requête affiche la plus grande profondeur atteinte lors d'une plongée ?

Bonne réponse : B

  1. Distracteur : SELECT MAX(*) FROM PLONGEE;Retour : MAX s'applique à une colonne précise, celle dont on veut la plus grande valeur : SQLite refuse MAX(*).
  2. Bonne réponse : SELECT MAX(profondeur) FROM PLONGEE;Retour : Oui : MAX renvoie la plus grande valeur de la colonne (25 m ici). Pas besoin de jointure : on ne demande que la valeur. MIN donnerait la plus petite.
  3. Distracteur : SELECT profondeur FROM PLONGEE ORDER BY profondeur;Retour : Ce tri est croissant : la première ligne est la profondeur la plus faible, et toutes les plongées sont affichées. Il faudrait DESC, ou plus simplement MAX.
  4. Distracteur : SELECT AVG(profondeur) FROM PLONGEE;Retour : AVG calcule la moyenne des profondeurs, pas la plus grande.

6. [Jointures] Deux colonnes de même nom

QCU, une seule réponse

Objectif : Préfixer un attribut par le nom de sa table pour lever une ambiguïté.

Les tables PLONGEUR (id_plongeur, nom, #id_club) et CLUB (id_club, nom) ont toutes deux un attribut nom.

Dans une jointure de ces deux tables, comment désigner le nom du plongeur ou de la plongeuse ?

Bonne réponse : A

  1. Bonne réponse : PLONGEUR.nomRetour : Oui : table.attribut lève l'ambiguïté. Sans préfixe, SQLite répondrait « ambiguous column name: nom ».
  2. Distracteur : nom.PLONGEURRetour : L'ordre est inversé : on écrit d'abord la table, puis l'attribut. Ici, SQLite répond « no such column: nom.PLONGEUR ».
  3. Distracteur : PLONGEUR->nomRetour : La flèche n'est pas la notation d'un attribut de table en SQL. On écrit la table, un point, puis l'attribut.
  4. Distracteur : PLONGEUR(nom)Retour : Les parenthèses servent aux fonctions. Ici, SQLite lit d'abord nom, qu'il trouve dans les deux tables, et répond « ambiguous column name ». On écrit PLONGEUR.nom.

7. [Jointures] Oublier la condition de liaison

QCU, une seule réponse

Objectif : Prévoir le résultat d'une requête sur deux tables sans condition de liaison.

La table PIROGUE a 4 lignes, la table VILLAGE en a 3. On exécute SELECT * FROM PIROGUE, VILLAGE;, sans condition.

Que se passe-t-il ?

Bonne réponse : C

  1. Distracteur : Le SGBD trouve tout seul la clé étrangère et fait la liaisonRetour : Le SGBD ne devine jamais la liaison : sans condition, il associe tout avec tout. C'est à la requête de dire quelles colonnes doivent être égales.
  2. Distracteur : La requête provoque une erreur, car la condition de jointure manqueRetour : La requête est valide : elle s'exécute. Mais elle donne toutes les combinaisons, ce qui n'est en général pas le résultat voulu.
  3. Bonne réponse : On obtient les 12 combinaisons : c'est un produit cartésienRetour : Oui : chaque pirogue est associée à chaque village, 4 × 3 = 12 lignes. Il faut une condition de jointure pour ne garder que les bonnes paires.
  4. Distracteur : La requête ne renvoie aucune ligne, faute de conditionRetour : C'est l'inverse : sans condition, aucune ligne n'est écartée. On obtient 4 × 3 = 12 lignes.

8. [Jointures] L'ordre des tables dans une jointure

QCU, une seule réponse

Objectif : Savoir qu'une jointure ne dépend pas de l'ordre des tables.

Dans une jointure A JOIN B ON …, l'ordre des tables (A JOIN B ou B JOIN A) change-t-il les lignes obtenues ?

Bonne réponse : D

  1. Distracteur : Oui, les données obtenues sont différentesRetour : La condition est la même dans les deux cas : les mêmes paires de lignes sont gardées. Seul l'ordre des colonnes avec SELECT * peut changer.
  2. Distracteur : Oui, SQL refuse l'un des deux sensRetour : Les deux sens sont acceptés : une jointure peut s'écrire à partir de n'importe laquelle des deux tables.
  3. Distracteur : Seulement si les tables ont plus de 100 lignesRetour : La taille des tables ne change pas le résultat d'une jointure : les paires gardées sont les mêmes dans les deux sens.
  4. Bonne réponse : Non, les lignes obtenues sont les mêmesRetour : Oui : la jointure garde les paires où la condition est vraie, dans un sens comme dans l'autre. Avec SELECT *, seules les colonnes changent de place.

9. [Jointures] Un alias de table avec AS

QCU, une seule réponse

Objectif : Comprendre le rôle d'un alias de table.

À quoi sert AS dans FROM PIROGUE AS P JOIN VILLAGE AS V ON P.id_v = V.id_v ?

Bonne réponse : C

  1. Distracteur : À trier les lignes des deux tables avant la jointureRetour : Le tri s'écrit ORDER BY, à la fin de la requête. AS donne un autre nom, plus court, à une table.
  2. Distracteur : À créer une copie de chaque table, le temps de la requêteRetour : Aucune table n'est copiée : P et V sont d'autres noms pour PIROGUE et VILLAGE, le temps de la requête.
  3. Bonne réponse : À donner un nom court à chaque table, dans la requêteRetour : Oui : P et V sont des alias. On écrit P.id_v au lieu de PIROGUE.id_v ; ils n'existent que dans cette requête.
  4. Distracteur : À protéger l'accès aux données des deux tablesRetour : Les droits d'accès se gèrent ailleurs, dans le SGBD. AS ne fait que renommer une table dans la requête.

10. [SQL] Renommer une colonne du résultat

QCU, une seule réponse

Objectif : Donner un autre nom à une colonne affichée.

Table : VILLAGE (id_v, nom_v).

Quelle requête affiche la colonne nom_v sous le titre village, sans modifier la table ?

Bonne réponse : A

  1. Bonne réponse : SELECT nom_v AS village FROM VILLAGE;Retour : Oui : AS donne un alias à la colonne, le temps de la requête. La table, elle, n'est pas modifiée.
  2. Distracteur : SELECT nom_v RENAME village FROM VILLAGE;Retour : RENAME sert à modifier la structure d'une table (ALTER TABLE … RENAME). Dans un SELECT, SQLite signale une erreur de syntaxe.
  3. Distracteur : SELECT nom_v IS village FROM VILLAGE;Retour : IS compare deux valeurs : SQLite cherche une colonne village pour la comparer à nom_v, et répond « no such column: village ».
  4. Distracteur : SELECT nom_v -> village FROM VILLAGE;Retour : La flèche ne renomme pas une colonne (dans SQLite, elle sert à lire du JSON) : SQLite cherche une colonne village et ne la trouve pas.

11. [SQL] Compter avec deux conditions

QCU, une seule réponse

Objectif : Filtrer avec AND avant de compter.

Table : TORTUE (id_t, espece, poids), poids en kg.

Quelle requête donne le nombre de tortues vertes de plus de 100 kg ?

Bonne réponse : B

  1. Distracteur : SELECT COUNT(*) FROM TORTUE WHERE espece = 'verte' OR poids > 100;Retour : OR compte aussi les tortues vertes légères et les grosses tortues d'autres espèces : le nombre est trop grand.
  2. Bonne réponse : SELECT COUNT(*) FROM TORTUE WHERE espece = 'verte' AND poids > 100;Retour : Oui : WHERE garde les tortues vertes de plus de 100 kg, puis COUNT(*) compte ces lignes.
  3. Distracteur : SELECT SUM(*) FROM TORTUE WHERE espece = 'verte' AND poids > 100;Retour : SUM additionne des valeurs, il ne compte pas des lignes, et SQLite refuse SUM(*).
  4. Distracteur : SELECT espece, poids FROM TORTUE WHERE espece = 'verte' AND poids > 100;Retour : Le filtre est bon, mais cette requête affiche les tortues une à une ; elle ne donne pas leur nombre. Il faut COUNT(*).

12. [SQL] Deux conditions sur les plongées

QCU, une seule réponse

Objectif : Combiner une condition sur un texte et une condition sur un nombre.

Table : PLONGEE (id_plongee, lieu, profondeur, #id_plongeur).

Quelle condition garde les plongées faites à Bandrélé à moins de 20 m de profondeur ?

Bonne réponse : D

  1. Distracteur : WHERE lieu = 'Bandrélé' OR profondeur < 20Retour : OR garderait aussi les plongées profondes de Bandrélé et les plongées peu profondes ailleurs. Les deux conditions doivent être vraies : AND.
  2. Distracteur : WHERE lieu = 'Bandrélé', profondeur < 20Retour : Les conditions ne se séparent pas par une virgule : SQLite signale une erreur de syntaxe.
  3. Distracteur : WHERE lieu = Bandrélé AND profondeur < 20Retour : Sans apostrophes, Bandrélé est lu comme un nom de colonne : SQLite répond « no such column: Bandrélé ». Un texte s'écrit entre apostrophes.
  4. Bonne réponse : WHERE lieu = 'Bandrélé' AND profondeur < 20Retour : Oui : AND garde les plongées qui remplissent les deux conditions à la fois.

13. [SQL] Trouver l'erreur dans une requête

QCU, une seule réponse

Objectif : Lire le message de SQLite et corriger l'écriture d'une valeur texte.

SQLite exécute la requête suivante et affiche le message d'erreur de la console.

SELECT nom FROM CLIENT WHERE ville = Mamoudzou;

Console :

Parse error: no such column: Mamoudzou

Pourquoi cette requête provoque-t-elle une erreur ?

Bonne réponse : B

  1. Distracteur : Le nom Mamoudzou doit être écrit en majusculesRetour : Les majuscules ne changent rien ici : MAMOUDZOU serait aussi lu comme un nom de colonne. Ce qui manque, ce sont les apostrophes.
  2. Bonne réponse : Il manque des apostrophes autour de MamoudzouRetour : Oui : sans apostrophes, SQLite cherche une colonne nommée Mamoudzou et répond « no such column: Mamoudzou ». On écrit ville = 'Mamoudzou'.
  3. Distracteur : On ne peut pas filtrer sur une villeRetour : On peut filtrer sur n'importe quel attribut. Le problème est l'écriture de la valeur.
  4. Distracteur : Il manque un point-virgule après SELECT nomRetour : Le point-virgule ne se met qu'à la fin de la requête complète, et il y est déjà.

14. [SQL] Limiter le nombre de lignes

QCU, une seule réponse

Objectif : Garder seulement les premières lignes d'un résultat.

Table : PLONGEE (id_plongee, lieu, profondeur, #id_plongeur).

Quelle requête n'affiche que les 3 premières lignes du résultat ?

Bonne réponse : A

  1. Bonne réponse : SELECT * FROM PLONGEE LIMIT 3;Retour : Oui : LIMIT, à la fin de la requête, garde les 3 premières lignes. Avec ORDER BY avant, on choisit lesquelles.
  2. Distracteur : SELECT TOP 3 * FROM PLONGEE;Retour : TOP existe dans certains SGBD, mais pas dans SQLite, qui signale une erreur. SQLite (comme MySQL) utilise LIMIT.
  3. Distracteur : SELECT * FROM PLONGEE STOP 3;Retour : STOP n'est pas un mot-clé SQL : SQLite signale une erreur de syntaxe.
  4. Distracteur : SELECT * FROM PLONGEE WHERE row < 3;Retour : row n'est pas une colonne de la table : SQLite répond « no such column: row ». Le nombre de lignes se limite avec LIMIT.

15. [Mises à jour] Supprimer une ligne encore référencée

QCU, une seule réponse

Objectif : Prévoir la réponse du SGBD quand une ligne supprimée est encore référencée.

Schéma : VILLAGE (id_v, nom_v) et PIROGUE (id_p, nom_p, couleur, #id_v). Le contrôle des clés étrangères est activé (dans SQLite : PRAGMA foreign_keys = ON).

On tente de supprimer un village alors que des pirogues y sont encore reliées. Que se passe-t-il ?

Bonne réponse : C

  1. Distracteur : Le village est supprimé, et toutes ses pirogues sont effacées avec luiRetour : Cela n'arrive que si la clé étrangère est déclarée avec ON DELETE CASCADE. Sans cette option, la suppression est refusée.
  2. Distracteur : Le village est supprimé, et la clé étrangère des pirogues passe à 0Retour : Le SGBD ne choisit jamais une valeur de remplacement tout seul. Sans option particulière, il refuse la suppression.
  3. Bonne réponse : La suppression est refusée, pour préserver l'intégrité référentielleRetour : Oui : supprimer le village laisserait des pirogues qui pointent vers un village inexistant. SQLite répond « FOREIGN KEY constraint failed ».
  4. Distracteur : Rien de spécial : la contrainte est ignoréeRetour : Le contrôle est activé : la contrainte est vérifiée à chaque modification. C'est son rôle.

16. [Mises à jour] Ajouter une ligne : INSERT

QCU, une seule réponse

Objectif : Écrire une requête INSERT INTO … VALUES.

Table : NAVIRE (nom, tonnage, port).

Quelle requête ajoute un navire nommé « Mamoudzou Express », de 400 tonnes ?

Bonne réponse : A

  1. Bonne réponse : INSERT INTO NAVIRE (nom, tonnage) VALUES ('Mamoudzou Express', 400);Retour : Oui : INSERT INTO table (colonnes) VALUES (valeurs) ajoute une ligne. Le port, non donné, reste vide (NULL).
  2. Distracteur : ADD INTO NAVIRE VALUES ('Mamoudzou Express', 400);Retour : Le mot-clé de l'ajout est INSERT INTO, pas ADD : SQLite signale une erreur de syntaxe.
  3. Distracteur : UPDATE NAVIRE SET nom = 'Mamoudzou Express';Retour : UPDATE modifie des lignes qui existent déjà : ici, il renommerait tous les navires ! Pour ajouter une ligne, on utilise INSERT.
  4. Distracteur : INSERT INTO NAVIRE ('Mamoudzou Express', 400);Retour : Il manque le mot-clé VALUES devant les valeurs : SQLite signale une erreur de syntaxe. On écrit INSERT INTO table (colonnes) VALUES (valeurs).

17. [Mises à jour] Modifier une ligne : UPDATE

QCU, une seule réponse

Objectif : Écrire un UPDATE … SET … WHERE qui ne modifie qu'une ligne.

Table : ECOLE (id_e, nom, ville).

Quelle requête change la ville de l'école n° 42 en « Mtsapéré » ?

Bonne réponse : B

  1. Distracteur : UPDATE ECOLE WHERE id_e = 42 SET ville = 'Mtsapéré';Retour : L'ordre est fixe : SET vient avant WHERE. Ici, SQLite signale une erreur de syntaxe.
  2. Bonne réponse : UPDATE ECOLE SET ville = 'Mtsapéré' WHERE id_e = 42;Retour : Oui : UPDATE table SET colonne = valeur WHERE condition. Seule la ligne n° 42 est modifiée.
  3. Distracteur : MODIFY ECOLE SET ville = 'Mtsapéré' WHERE id_e = 42;Retour : MODIFY n'est pas un mot-clé SQL : une modification de lignes s'écrit avec UPDATE.
  4. Distracteur : UPDATE ECOLE SET ville = 'Mtsapéré';Retour : Attention : sans WHERE, toutes les écoles de la table seraient placées à Mtsapéré. Le WHERE choisit les lignes à modifier.

18. [Mises à jour] Un UPDATE qui calcule

QCU, une seule réponse

Objectif : Utiliser la valeur actuelle d'une colonne dans un UPDATE.

Table : RESERVOIR (id_r, nom, volume), volume en m³.

Quelle requête augmente de 10 m³ le volume de tous les réservoirs ?

Bonne réponse : A

  1. Bonne réponse : UPDATE RESERVOIR SET volume = volume + 10;Retour : Oui : pour chaque ligne, la nouvelle valeur est calculée à partir de l'ancienne. Sans WHERE, toutes les lignes sont concernées, comme demandé.
  2. Distracteur : SET volume = volume + 10 FROM RESERVOIR;Retour : Une requête de modification commence par UPDATE : ici, SQLite signale une erreur de syntaxe.
  3. Distracteur : UPDATE RESERVOIR volume + 10;Retour : Il manque SET et le signe = : on doit dire quelle colonne reçoit quelle valeur.
  4. Distracteur : SELECT volume + 10 FROM RESERVOIR;Retour : SELECT affiche les volumes augmentés, mais n'enregistre rien : la table n'est pas modifiée.

19. [Mises à jour] Supprimer une ligne : DELETE

QCU, une seule réponse

Objectif : Écrire un DELETE FROM … WHERE.

Table : NAVIRE (nom, tonnage, port).

Quelle requête supprime le navire nommé « Vieux Port » ?

Bonne réponse : C

  1. Distracteur : REMOVE FROM NAVIRE WHERE nom = 'Vieux Port';Retour : REMOVE n'est pas un mot-clé SQL : la suppression de lignes s'écrit DELETE FROM.
  2. Distracteur : DELETE nom = 'Vieux Port' FROM NAVIRE;Retour : La condition se place après FROM, dans un WHERE : DELETE FROM table WHERE condition. Ici, SQLite signale une erreur.
  3. Bonne réponse : DELETE FROM NAVIRE WHERE nom = 'Vieux Port';Retour : Oui : DELETE FROM, suivi d'un WHERE, supprime seulement les lignes qui vérifient la condition.
  4. Distracteur : DROP FROM NAVIRE WHERE nom = 'Vieux Port';Retour : DROP supprime une table entière (DROP TABLE), pas une ligne. Il ne s'écrit pas avec FROM et WHERE.

20. [Mises à jour] Supprimer une table entière

QCU, une seule réponse

Objectif : Distinguer la suppression des lignes et la suppression de la table.

Quelle requête supprime définitivement la table NAVIRE, avec toutes ses données ?

Bonne réponse : D

  1. Distracteur : DELETE TABLE NAVIRE;Retour : SQLite signale une erreur de syntaxe : DELETE s'écrit DELETE FROM et supprime des lignes, jamais la table elle-même.
  2. Distracteur : REMOVE TABLE NAVIRE;Retour : REMOVE n'est pas un mot-clé SQL. La suppression d'une table s'écrit DROP TABLE.
  3. Distracteur : DELETE * FROM NAVIRE;Retour : L'étoile n'a pas sa place dans un DELETE : SQLite signale une erreur. DELETE FROM NAVIRE; viderait la table, mais la garderait.
  4. Bonne réponse : DROP TABLE NAVIRE;Retour : Oui : DROP TABLE détruit la table, sa structure et son contenu. Après, toute requête sur NAVIRE échoue : « no such table ».
